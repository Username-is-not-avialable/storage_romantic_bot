# WEB_FRONTEND: веб-интерфейс (React)

Документ фиксирует целевой стек, способ сборки и размещение UI рядом с API на одном хосте (рекомендуемый для cookie-сессии вариант).

## 1. Цели

- Один пользовательский **origin**: браузер ходит на `https://<домен>/` и `https://<домен>/api/...` (без второго поддомена под API).
- **React** SPA, понятная структура по фичам, переиспользуемые компоненты.
- **shadcn/ui** (Radix + Tailwind): готовая доступная типографика, формы и layout «из коробки», при этом компоненты лежат в репозитории и их можно править.
- В Docker: один сервис `web`, внутри **Nginx** отдаёт статику и проксирует `/api` на контейнер `api`.

## 2. Стек (зафиксировано)

| Слой | Выбор |
|------|--------|
| Сборка | Vite |
| UI | React 19 + TypeScript |
| Маршруты | React Router |
| Серверное состояние | TanStack Query (рекомендуется при появлении вызовов API) |
| Стили / компоненты | Tailwind CSS + **shadcn/ui** |

## 3. Обращение к API и сессия

- Роутеры FastAPI уже с префиксом **`/api/...`** (`/api/auth`, `/api/gear`, … в коде приложения).
- В **продакшене за одним Nginx** запросы к API идут на **относительный путь** `/api/...` (тот же хост и порт, что и SPA) — браузер отправляет cookie сессии без настройки CORS между разными доменами.
- В **локальной разработке** (Vite на отдельном порту): в `vite.config` настроен **proxy** `/api` → бэкенд (по умолчанию `http://127.0.0.1:8100`, переопределение через env **`VITE_DEV_API_PROXY_TARGET`**), чтобы cookie и пути вели себя как в проде.

Переменные окружения фронта (префикс `VITE_`):

| Переменная | Назначение |
|------------|------------|
| `VITE_API_BASE_URL` | Пустая строка в типичном деплое (пути вида `/api/...`). Нестандартный базовый URL только если понадобится отладка без proxy. |

## 4. Структура каталога `web/` (ориентир)

- `src/routes/` — страницы и композиция layout.
- `src/features/` — доменные области (`auth`, `catalog`, заявки, аренды, админка).
- `src/api/` — клиент (`fetch`, `credentials: 'include'`, разбор ошибок).
- `src/components/` — общие блоки без привязки к домену.
- `src/components/ui/` — компоненты shadcn (генерируемые CLI).

RBAC на фронте: **ужесточение UX** (скрыть пункты меню, редирект). Истина прав доступа только на сервере.

## 5. Docker и Compose

Сервис **`web`** собирается многоступенчатым Dockerfile:

1. Этап **build**: Node устанавливает зависимости и выполняет `npm run build` → статика в `dist/`.
2. Этап **runtime**: образ `nginx:alpine`, копируется `dist/`, подключается `web/nginx.conf`.

`nginx.conf`:

- **`location /api/`** — `proxy_pass` на `http://api:8000` (хостнейм сервиса Compose `api`).
- **`location /`** — раздача статики SPA и **`try_files ... /index.html`** для клиентской маршрутизации React Router.

В Compose сервис `web` публикуется как **`${WEB_PUBLISH_PORT:-8080}:80`** (переменная окружения на хосте). На VPS можно выставить `WEB_PUBLISH_PORT=80` или поставить reverse proxy/TLS перед контейнером.

Контейнер `api` по умолчанию проброшен на хост `:8100` для отладки; для «только один вход» снаружи достаточно ходить в приложение через `web`, а проброс порта API с хоста убрать.

### Локальная разработка на WSL/macOS/Linux

Ставить зависимости и собирать фронт удобно так:

```bash
cd web
npm install
npm run dev
```

Если `npm install`/`esbuild` ругаются из‑за смешения **Windows‑npm** и путей `\\wsl.localhost\...`, используйте **Node внутри WSL**, либо однократно:

```bash
docker run --rm -v "$(pwd)/web:/app" -w /app node:22-alpine sh -c "npm install && npm run build"
```

Образ сборки приложения описан в `web/Dockerfile` (там же воспроизводимые `npm ci` и билд).

При необходимости TLS терминацию (HTTPS) добавляют **перед** этим стеком (отдельный reverse proxy или облачный балансировщик): для cookie и `Secure` нужен HTTPS на пользовательском домене.
