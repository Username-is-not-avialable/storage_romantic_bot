# TECH_SPEC: Система учета и выдачи туристского снаряжения

## 1. Цель документа
Документ фиксирует техническую спецификацию MVP и ближайших итераций системы учета, бронирования и выдачи снаряжения для некоммерческого клуба.

## 2. Контекст и ограничения
- Тип системы: веб-приложение с API и VK-ботом.
- Целевая нагрузка: 2-3 одновременных пользователя в среднем, до 10 в пике.
- Объем данных: несколько сотен единиц снаряжения.
- Офлайн-режим: не требуется.
- Стек: Python API, open-source компоненты.

## 3. Ролевая модель и права
### 3.1 Участник
- Регистрация/аутентификация.
- Просмотр каталога и доступности.
- Создание заявок на бронирование и продление.
- Просмотр своих активных аренд.
- Просмотр статуса членского взноса.
- Получение уведомлений.

### 3.2 Завснар
- Все права участника.
- Обработка входящих заявок (подтвердить/отклонить с комментарием).
- Операции выдачи/приема.
- CRUD снаряжения.
- Корректировка записей аренды в исключительных случаях.
- Списки должников, активных аренд, история участника.

### 3.3 Администратор
- Назначение/снятие роли завснара.
- Управление учетными записями.
- Базовые системные настройки (в рамках MVP - ограниченно).

## 4. Архитектура
### 4.1 Логические компоненты
- `API Core` (FastAPI): REST эндпоинты, валидация, RBAC.
- `Domain Services`: бизнес-логика заявок, аренд, доступности.
- `Persistence`: PostgreSQL, SQLAlchemy ORM.
- Веб-интерфейс (React SPA + shadcn/ui): сборка и публикация через Nginx совместно с API — см. [WEB_FRONTEND.md](WEB_FRONTEND.md).
- `Integrations`:
- Архитектура диалогов бота: [BOT_DIALOG.md](BOT_DIALOG.md)
  - VK bot adapter
  - Sync adapter для статуса взносов (Excel)
- `Notification Service`: отправка сообщений по событию и по расписанию.
- `Scheduler/Workers`: периодические задачи (просрочки, reminders, sync).

### 4.2 Принципы расширяемости
- VK-бот реализуется как адаптер поверх общего service-layer.
- Бизнес-правила не дублируются в боте, только в API/services.
- Каналы доставки уведомлений расширяются без изменения ядра домена.

### 4.3 Делегированная идентификация пользователя для VK-бота
**Решение (зафиксировано):** действия от имени пользователя в VK вызываются не произвольным HTTP-клиентом по одному `vk_user_id`, а **доверенным процессом бота**, который передаёт:
- заголовок `X-VK-Bot-Secret` (общий секрет API и бота, как для привязки аккаунта);
- идентификатор `vk_user_id` (числовой id пользователя VK в событии Long Poll / Callback).

**На стороне API:** единая зависимость FastAPI `get_user_for_vk_bot` (или эквивалентное имя в коде), которая:
1. Проверяет секрет (тот же механизм, что у `POST /api/integrations/vk/link-complete` и `GET /api/integrations/vk/me`).
2. Находит внутреннего пользователя по `user_messenger_links` с `provider=vk` и `external_user_id=str(vk_user_id)`.
3. Возвращает сущность `User` для вызова существующих domain/service-функций **без дублирования бизнес-правил**.

Отсутствие привязки VK к учётной записи — явная ошибка (например `404`); неверный секрет — `401`. Произвольный вызов «только с `vk_user_id`» без секрета бота **не допускается** (защита от подделки id).

План внедрения зависимости и маршрутов см. [VK_BOT_API_AUTH_PLAN.md](VK_BOT_API_AUTH_PLAN.md).

## 5. Модель данных (MVP + next)
### 5.1 Сущности MVP (частично уже есть)
- `User`: внутренний `id`, `email`, `password_hash`, `email_verified_at`, `is_active`, `full_name`, `phone`, `document`, `role`.
- `UserMessengerLink`: привязка пользователя к VK (`provider`=`vk`, `external_user_id` — id пользователя VK).
- `Gear`: name, description, total_quantity, available_count.

### 5.2 Аренда и возвраты (целевой дизайн: 4 таблицы)
Цель: не терять историю при частичных возвратах и хранить отдельные факты:
1) первоначальная выдача (с полным составом),
2) одно или несколько событий частичного возврата,
3) событие окончательного возврата.

Подход: аренда моделируется как документ (`rentals`) + строки состава (`rental_items`) + события (`rental_events`) + строки событий возврата (`rental_event_items`).

#### 5.2.1 `rentals` (шапка аренды)
- Назначение: общие поля аренды, единая точка ссылок для событий/отчетов.
- Поля (минимум):
  - user_id (internal user id)
  - issue_manager_id (internal user id)
  - issue_date
  - due_date
  - event (название мероприятия)
  - comment
  - status: `active` | `closed` (может вычисляться, но удобен для быстрых выборок)
  - closed_at (nullable)

#### 5.2.2 `rental_items` (состав выдачи)
- Назначение: фиксирует первоначальный состав аренды (что и сколько было выдано).
- Поля (минимум):
  - rental_id (FK -> rentals.id)
  - gear_id (FK -> gear.id)
  - qty_issued (целое > 0)
- Ограничения:
  - `UNIQUE(rental_id, gear_id)` (одна строка на тип снаряжения в рамках аренды)

#### 5.2.3 `rental_events` (события по аренде)
- Назначение: append-only журнал событий жизненного цикла аренды (аудит и история).
- Типы событий (минимум):
  - `ISSUE` (выдача оформлена, запрос принят)
  - `RETURN_PARTIAL` (частичный возврат)
  - `RETURN_FINAL` (окончательный возврат; после него аренда закрыта)
- Поля (минимум):
  - rental_id (FK -> rentals.id)
  - type (enum)
  - created_at (timestamp события)
  - manager_id (internal user id менеджера, оформившего событие)
  - comment (nullable)
- fee_status_snapshot (nullable): снапшот статуса активности членского взноса, доступного на момент создания события (например: `active`, `inactive`, `unknown`, `missing`); используется для аудита и объяснения решений даже при задержках синхронизации из Excel.
- Принцип: события не редактируются “задним числом” (append-only). Исправления делаются отдельным событием (опционально `CORRECTION`) с указанием причины.

#### 5.2.4 `rental_event_items` (строки событий возврата)
- Назначение: хранит содержимое конкретного события возврата.
- Важное правило: в этой таблице хранятся **только фактически возвращенные позиции** (то, что реально сдали в рамках данного события).
- Поля (минимум):
  - rental_event_id (FK -> rental_events.id)
  - gear_id (FK -> gear.id)
  - qty_returned (целое > 0)
  - condition / damage_notes (nullable; при необходимости для фиксации состояния)
- Ограничения:
  - `UNIQUE(rental_event_id, gear_id)` (в одном событии один тип снаряжения не дублируется)

#### 5.2.5 Заявка на возврат (`rental_return_requests` + `rental_return_request_items`)
- Назначение: участник инициирует сдачу по активной аренде; завснар (или админ) подтверждает или отклоняет. Фактический возврат при подтверждении выполняется тем же путём, что и менеджерский приём: через события `RETURN_PARTIAL` / `RETURN_FINAL` (сервис `return_rental`), без дублирования логики инвентаря.

**`rental_return_requests` (шапка):**
- `user_id` (FK → `users.id`) — инициатор; должен совпадать с владельцем `rentals.user_id` для указанной аренды.
- `rental_id` (FK → `rentals.id`) — аренда, по которой сдают.
- `target_manager_id` (FK → `users.id`, nullable) — выбранный завснар; если задан, решение принимает этот менеджер либо администратор (обход для согласованности процессов).
- `status`: `pending` | `approved` | `rejected`
- `created_at`, `decision_manager_id`, `decision_comment` (как у заявок на выдачу).

**`rental_return_request_items` (строки заявки):**
- `rental_return_request_id`, `gear_id`, `qty_return` (> 0)
- `UNIQUE(rental_return_request_id, gear_id)`

**Политика непересечения:** не более одной заявки в статусе `pending` на одну `rental_id` (проверка в сервисе + частичный уникальный индекс по БД).

### 5.3 Обязательные расширения
- `Role`/`UserRole`: явные роли (`member`, `manager`, `admin`) вместо одного `is_manager`.
- `BookingRequest` (`rental_requests` + `rental_request_items`):
  - статус: `pending`, `approved`, `rejected`, `cancelled`, `expired`
  - состав: позиции и количества
  - залоговый документ
  - дата планируемого возврата
  - мероприятие, комментарий, причина отклонения
- `ExtensionRequest`: запросы продления аренды.
- `MembershipStatus`: статус взноса, дата окончания, источник, timestamp синхронизации.
- `NotificationLog`: канал, тип, payload, статус отправки.
- `AuditLog`: кто/когда менял критичные данные.

## 6. Бизнес-правила
- Нельзя подтверждать бронирование при недостатке `available_count`.
- Выдача уменьшает `available_count`, прием увеличивает.
- Для частичного возврата аренда остается активной до полного возврата.
- Частичный/окончательный возврат фиксируется через `rental_events` + `rental_event_items` (append-only), без “перезаписи истории”.
- Нельзя вернуть больше, чем было выдано по позиции:
  - для каждой пары `(rental_id, gear_id)` суммарно возвращенное `qty_returned` по всем событиям не должно превышать `qty_issued`
- Аренда закрывается (`status=closed`) только когда для всех позиций выполняется:
  - для каждой позиции остаток `qty_issued - суммарно_возвращенное_qty_returned` должен быть равен 0
- Просрочка = `status = active` и `due_date < today` (т.е. аренда не закрыта и срок уже прошел).
- Продление возможно только для активной и просроченной аренды.
- Правила допуска при неактивном/отсутствующем/неизвестном взносе:
  - одобрение бронирований и выдача разрешены при любом статусе взноса на момент `approve/issue`;
  - факт того, какой статус завснар видел в этот момент, фиксируется append-only снапшотом `rental_events.fee_status_snapshot` (при issue/returns);
  - обновление `MembershipStatus` из Excel не перезаписывает уже созданные события.

## 7. API-контракты (целевые)
### 7.1 Аутентификация и профиль
- Способ аутентификации: `email + password` (web).
- Сохранение сессии (web): серверная сессия в `httpOnly` cookie.
- Вход в VK-бот: инициируется по ссылке на страницу аутентификации на сайте; после входа выполняется обратный редирект/возврат в бота.
- Сохранение сессии в боте: персистентная привязка аккаунта (без повторного ввода пароля пользователем; навсегда).
- Email для регистрации/сброса пароля: отправка кодов подтверждения через Gmail API (OAuth, MVP-вариант).
- `POST /api/auth/login` (web)
- `POST /api/auth/logout`
- `POST /api/auth/request-code`
- `POST /api/auth/verify-code`
- `GET /api/auth/me`

#### 7.1.1 Действия пользователя через VK-бота (помимо web-сессии)
Контур **не заменяет** web-login: пароль и регистрация остаются на сайте. После привязки VK (`user_messenger_links`) бот вызывает эндпоинты с `X-VK-Bot-Secret` + `vk_user_id`; сервер через **`Depends(get_user_for_vk_bot)`** получает того же `User`, что и при сессии в браузере, и применяет те же RBAC-ограничения на уровне сервисов/роутеров.

Минимальный набор integration-эндпоинтов (целевой, по мере внедрения): см. [VK_BOT_API_AUTH_PLAN.md](VK_BOT_API_AUTH_PLAN.md). Уже реализовано без этой зависимости: выдача кода привязки с сайта (`POST /api/auth/vk-link/request_code`, web-auth), завершение привязки и чтение профиля ботом (`POST /api/integrations/vk/link-complete`, `GET /api/integrations/vk/me`). Справочник завснаров и администраторов с привязкой VK для бота (`GET /api/integrations/vk/managers`, только `X-VK-Bot-Secret`).

**Зафиксированное решение по URL:** действия, которые в браузере выполняются с cookie-сессией, а из процесса VK-бота — с `X-VK-Bot-Secret` и `vk_user_id`, для бота **выставляются отдельными маршрутами** под префиксом `/api/integrations/vk/`, по смыслу зеркалирующими канонические пути из §7.3–§7.4 (конкретный список и контракт — в плане по ссылке выше). Так явно разделены публичный web-контур и доверенный интеграционный контур бота; усложняется случайная конфигурация «двойной» аутентификации на одном URL. **Доменная логика не дублируется:** вызываются те же функции сервисного слоя. Полное копирование длинных тел FastAPI-обработчиков между web и VK **нежелательно** — общие шаги (валидации доступа к сущности, вызов сервиса, сбор ответа) выносятся в переиспользуемые функции; см. правила в `.cursor/rules/project-standards.mdc` (раздел про дублирующиеся роутеры).

### 7.2 Каталог и доступность
- `GET /api/gear?query=&page=&limit=`
- `GET /api/gear/{id}`
- `GET /api/availability?gear_id=&from=&to=`

### 7.3 Заявки на выдачу (rental requests; не путать с бронированием)
- `GET /api/rental-requests` — список заявок текущего пользователя (опционально `status`, `sort_order`).
- `POST /api/rental-requests`
- `PATCH /api/rental-requests/{id}` (изменение состава/полей пока `pending`)
- `PATCH /api/manager/rental-requests/{id}` (approve/reject + comment)

### 7.3.1 Заявки на возврат по аренде (`rental_return_requests`)
- `GET /api/rental-return-requests` — список заявок на возврат текущего пользователя (опционально `status`).
- `POST /api/rental-return-requests` — участник: `rental_id`, строки `(gear_id, qty_return)` в пределах остатка по аренде, опционально `target_manager_id` (`users.id`).
- `GET /api/manager/rental-return-requests` — очередь для завснара/админа (опционально `status`, `user_id`).
- `PATCH /api/manager/rental-return-requests/{id}` — завснар/админ: `approve` / `reject` и комментарий; при `approve` в одной транзакции вызывается тот же поток, что и для `PATCH /api/rentals/{id}/return` (делегирование в `return_rental`).

### 7.4 Аренды
- `POST /api/rentals/issue`
- `PATCH /api/rentals/{id}/return`
- `GET /api/rentals/active`
- `GET /api/rentals/debtors`
- `POST /api/rentals/{id}/extension-requests`

### 7.5 Администрирование
- `PATCH /api/admin/users/{id}/roles`
- `GET /api/admin/users`

## 8. Интеграция взносов (Excel)
### 8.1 Источник
- Excel-файл, поддерживаемый казначеем (ручное заполнение).

### 8.2 Минимальный pipeline
- Загрузка файла по расписанию или вручную.
- Валидация схемы колонок (идентификатор участника, дата окончания, статус).
- Upsert в `MembershipStatus`.
- Лог ошибок разбора строк, метрика успешной синхронизации.

### 8.3 Идентификация пользователя
- Предпочтительно: сопоставление по `user_messenger_links` (`provider=vk`, `external_user_id`).
- Запасной вариант: телефон + full_name (с ручной верификацией).

## 9. Уведомления
- Событийные:
  - новая заявка -> завснар
  - решение по заявке -> участник
- Периодические:
  - напоминание о возврате (T-2/T-1)
  - уведомление о просрочке (ежедневно до закрытия)
- Каналы: web + VK.

## 10. Нефункциональные требования
- P95 отклик основных операций: до 2-3 секунд.
- Доступность: 24/7, с оговоркой на инфраструктуру хоста.
- Безопасность:
  - разграничение ролей,
  - серверная валидация прав,
  - маскирование персональных данных в логах.
- Надежность:
  - регулярные бэкапы БД,
  - миграции схемы через Alembic,
  - транзакционность критичных операций (issue/return/approve).
- Масштабируемость:
  - адаптерная модель каналов,
  - отделение API и background jobs.

## 11. Текущее состояние реализации (по коду)
- Есть каркас FastAPI, сущности `User`, `Gear`, `Rental`.
- Есть базовые роуты для пользователей, снаряжения и аренд.
- Реализованы роли `admin/member/manager` и RBAC-проверки на защищенных эндпоинтах.
- Реализована web-аутентификация (`/api/auth/login`, `/api/auth/logout`, `/api/auth/me`) через cookie-сессию.
- Добавлены auth email-code endpoints (`/api/auth/request-code`, `/api/auth/verify-code`) и отправка через Gmail API (OAuth, MVP).
- Идентификация пользователей переведена на внутренний `users.id`; привязка VK — в `user_messenger_links` (`provider=vk`).
- Нет отдельного слоя бронирований (bookings), продлений и задолженностей как отдельной модели.
- Нет интеграции Excel-взносов, VK-адаптера и планировщика уведомлений.

## Appendix A: Миграции БД (Alembic)

Команды запуска (из директории `api/`):

- Создать новую миграцию (ручную):
  - `alembic -c alembic.ini revision -m "msg"`
- Создать миграцию автогенерацией от текущих моделей:
  - `alembic -c alembic.ini revision --autogenerate -m "msg"`
- Применить миграции:
  - `alembic -c alembic.ini upgrade head`
- Откатить последнюю миграцию:
  - `alembic -c alembic.ini downgrade -1`
